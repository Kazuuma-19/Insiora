# 0015. API のモック

## 決定

MSW（Mock Service Worker）を採用する。モックのハンドラーは orval（[0012](0012-frontend-codegen.md)）で OpenAPI から生成する。次の 2 つの用途で使う。

- 開発: backend の実装がなくても、TypeSpec で定義した API を使って画面を作る
- テスト: Vitest と React Testing Library のテスト（[0009](0009-frontend-test.md)）で、API の応答を差し替える

E2E テスト（[0010](0010-e2e-test.md)）では使わず、本物の backend につなぐ。

### 理由

- API を先に定義する（[0011](../common/0011-api-definition.md)）ので、モックがあれば backend より先に frontend を作れる
- orval がハンドラーを生成するため、手書きがほとんど要らない
- 同じハンドラーを、ブラウザでの開発と Node でのテストの両方で使える
- ネットワーク層で横取りするため、アプリのコードをモックのために変えなくてよい

## 比較案

| 案 | 名称 | バージョン | 特徴 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | MSW | 3.0.6 | ネットワーク層で横取り、開発とテストで共用 | 採用 |
| 2 | テストごとのモック | — | fetch や API 関数を個別にモック | 見送り |
| 3 | 別のモックサーバー（Prism など） | — | OpenAPI からサーバーを起動 | 見送り |

## 案1: MSW

### 概要

Service Worker（ブラウザ）や Node のリクエストの横取りを使い、ネットワーク層で API の応答を差し替えるライブラリ。

### メリット

- アプリのコードを変えずにモックできる
- 同じハンドラーを開発とテストの両方で使える
- orval がハンドラーを生成する

### デメリット

- 生成されるモックの値はランダムなので、テストで特定の値が必要な場合は、ハンドラーを上書きする

## 案2: テストごとに fetch や API 関数をモックする

### 概要

Vitest の `vi.mock` などで、テストごとに fetch や API 関数を置き換える方法。

### メリット

- 追加のライブラリが不要

### デメリット

- テストごとにモックを書く必要があり、開発中の画面確認には使えない
- 実装の詳細（どの関数を呼ぶか）にテストが依存する

## 案3: モックサーバーを別に立てる（Prism など）

### 概要

OpenAPI を読み込んで、モックの API サーバーを別のプロセスとして起動する方法。

### メリット

- frontend 以外からも使える

### デメリット

- 別のプロセスを起動する必要がある
- テストでの値の差し替えがしにくい
