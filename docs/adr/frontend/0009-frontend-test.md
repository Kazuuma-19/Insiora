# 0009. frontend のテスト

## 決定

テストランナーに Vitest、コンポーネントのテストに React Testing Library、ブラウザ環境に jsdom を採用する。

### 理由

テストランナー（Vitest）

- Vite の設定（`vite.config.ts`）をそのまま使え、テスト用の設定を別に持たなくてよい
- TypeScript と ESM が追加の設定なしで動く
- Jest とほぼ同じ書き方で、情報を流用できる

コンポーネントのテスト（React Testing Library）

- 実装の詳細ではなく、利用者の操作（ボタンを押す、文字を入力する）に近い形でテストでき、リファクタリングに強い
- React のテストで最も広く使われていて、情報が多い
- ブラウザ環境（jsdom など）と組み合わせて速く動き、本物のブラウザを起動しなくてよい

ブラウザ環境（jsdom）

- Web の標準仕様への準拠を重視していて、テスト環境に特有の動きの違いで困りにくい
- React Testing Library と組み合わせた情報が最も多い
- テストの数がまだ少なく、happy-dom の速さの利点が効くのは先になる
- Vitest の設定で環境を切り替えられるため、遅さが問題になれば happy-dom に移りやすい

## テストランナー

### 案1: Vitest

#### 概要

Vite をベースにしたテストランナー。Jest と互換性の高い API を持つ。

#### メリット

- `vite.config.ts` の設定をそのまま使える
- TypeScript が追加の設定なしで動く
- Jest とほぼ同じ書き方ができる

#### デメリット

- Jest に比べると、情報や実績はまだ少ない

### 案2: Jest

#### 概要

Meta 製の、JavaScript の標準的なテストランナー。

#### メリット

- 歴史が長く、実績と情報が多い

#### デメリット

- Vite や ESM と組み合わせるには、追加の設定が必要

## コンポーネントのテスト

### 案1: React Testing Library

#### 概要

コンポーネントを描画し、画面に表示された文字や役割（ボタン、見出しなど）で要素を探して操作・検証するライブラリ。`@testing-library/jest-dom` と組み合わせて、「表示されている」などの検証を書く。

#### メリット

- 利用者の操作に近い形でテストでき、コンポーネントの内部の書き方を変えてもテストが壊れにくい
- 役割で要素を探すため、アクセシビリティを意識した作りになりやすい
- React のテストで最も広く使われていて、情報が多い

#### デメリット

- ブラウザ環境を再現して動かすため、レイアウトや CSS に関わる動きは確認できない

### 案2: vitest-browser-react

#### 概要

Vitest Browser Mode（ブラウザ環境の案3）で、コンポーネントを本物のブラウザに描画してテストするライブラリ。React Testing Library に近い書き方ができる。

#### メリット

- 本物のブラウザで動くため、再現による動きの違いがない
- レイアウトや CSS に関わる処理も確認できる

#### デメリット

- ブラウザを起動するため、jsdom などで動かすより遅い
- 情報が React Testing Library より少ない

### 案3: Storybook のインタラクションテスト

#### 概要

UI カタログの Storybook で作った Story（コンポーネントの表示例）に操作と検証を書き、Vitest で実行する方法。

#### メリット

- Story をそのままテストに使え、画面で動きを確認しながら書ける

#### デメリット

- Storybook の導入と、Story の作成・保守が必要になる
- UI ライブラリを使わず画面の数も多くない今の規模では、仕組みとして重い

### 案4: Enzyme

#### 概要

コンポーネントの内部（state や props）を直接検査できるテストライブラリ。

#### メリット

- コンポーネントの内部の状態を細かく検査できる

#### デメリット

- 最後のリリースが 2022 年で、最近の React に公式には対応していない
- 内部の実装に依存したテストになり、リファクタリングで壊れやすい

## ブラウザ環境

### 案1: jsdom

#### 概要

Node 上で DOM や Web API を再現するライブラリ。Vitest のテスト環境として指定して使う。

#### メリット

- Web の標準仕様への準拠を重視している
- 歴史が長く、React Testing Library と組み合わせた情報が最も多い

#### デメリット

- happy-dom より遅く、メモリも多く使う
- Canvas や要素の大きさの計算などは再現されず、グラフの描画は確認できない

### 案2: happy-dom

#### 概要

速さを重視して作られた、Node 上で DOM を再現するライブラリ。

#### メリット

- jsdom より速く、軽い

#### デメリット

- 一部の API は実装されていないか、動きが標準と違う場合がある
- 問題が起きたときの情報が jsdom より少ない
- jsdom と同じく、グラフの描画は確認できない

### 案3: Vitest Browser Mode

#### 概要

DOM を再現せず、Playwright などで本物のブラウザを起動して、Vitest のテストを実行する仕組み。

#### メリット

- 本物のブラウザのため、再現による動きの違いがない
- レイアウト、CSS、Canvas などの描画も確認できる

#### デメリット

- ブラウザを起動するため、jsdom や happy-dom より遅い
- 設定が増え、CI でもブラウザの準備が必要になる
