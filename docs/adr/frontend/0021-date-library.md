# 0021. frontend の日付ライブラリ

## 決定

Temporal を採用する。未対応のブラウザ向けに temporal-polyfill を使う。

### 理由

- Insiora の中心は、Toggl の時間記録を利用者のタイムゾーンで日や週に区切って集計・表示すること。タイムゾーン付きの日時、日付だけ、時間の長さを型で区別できる Temporal が合う
- 型が分かれているため、日付だけの値と日時を取り違えたり、日の区切りを間違えたりしにくい
- JavaScript の標準 API（TC39 で Stage 4）のため、ブラウザが対応すればライブラリが不要になり、入れ替えも発生しない
- Firefox（139）、Chrome / Edge（144）はすでに対応していて、未対応の Safari は polyfill で補える

## 比較案

| 案 | 名称 | バージョン | 特徴 | 判定 |
| --- | --- | --- | --- | --- |
| 1 | Temporal + temporal-polyfill | polyfill 1.0.8 | 標準 API、日時・日付・期間の型が分かれる | 採用 |
| 2 | date-fns + @date-fns/tz | 4.4.0 / 1.5.0 | 関数単位で import、利用者が多い | 次点 |
| 3 | Day.js | 1.11.23 | 非常に小さい | 見送り |
| 4 | Luxon | 3.7.2 | タイムゾーンと期間を標準で扱う | 見送り |

## 案1: Temporal + temporal-polyfill

### 概要

JavaScript の `Date` に代わる、新しい標準の日付・時刻 API。日時（`Instant`、`ZonedDateTime`）、日付だけ（`PlainDate`）、時間の長さ（`Duration`）などの型を持つ。未対応のブラウザでは polyfill で使う。

### メリット

- タイムゾーン付きの日時、日付だけ、時間の長さを型で区別できる
- 値は変更不可（immutable）で、意図しない書き換えが起きない
- 標準 API のため、将来はライブラリが不要になる

### デメリット

- Safari の安定版が未対応で、当面は polyfill が必要
- 新しい API のため、情報はまだ少ない
- 日付の書式は `Intl.DateTimeFormat` と組み合わせる必要がある

## 案2: date-fns + @date-fns/tz

### 概要

JavaScript の `Date` を操作する関数の集まり。v4 からは `@date-fns/tz` でタイムゾーンを公式に扱える。

### メリット

- 使う関数だけを import するので、バンドルが小さい
- 利用者と情報が多い

### デメリット

- 中身は `Date` のため、日付だけ、日時、時間の長さを型で区別できない

## 案3: Day.js

### 概要

Moment.js に似た書き方の、非常に小さい日付ライブラリ。

### メリット

- 非常に小さく、書き方が簡単

### デメリット

- タイムゾーンや所要時間の機能は、プラグインで追加する必要がある
- 型の区別がない

## 案4: Luxon

### 概要

タイムゾーンと時間の長さ（`Duration`）を最初から扱える日付ライブラリ。

### メリット

- タイムゾーンと所要時間を追加なしで扱える

### デメリット

- 最後のリリースが 2025 年 9 月で、更新が少ない
- Temporal と役割が重なり、標準化された後は移行が必要になる
