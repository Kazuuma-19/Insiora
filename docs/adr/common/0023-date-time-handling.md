# 0023. 日時の扱い

## 決定

システム全体で、日時は UTC で保存・受け渡しし、利用者のタイムゾーンへの変換は集計と表示の時だけ行う。

| 場所 | 扱い |
| --- | --- |
| DB | `timestamptz` で保存する（UTC） |
| backend | java.time の `Instant` で扱う。集計で日や週を区切る時は、利用者のタイムゾーン（`ZoneId`）を使う |
| API | ISO 8601 の文字列でやりとりする。日時は UTC（`2026-11-18T12:00:00Z`）、日付だけの値は `2026-11-18` |
| frontend | Temporal の型で扱い、表示の時に利用者のタイムゾーンに変換する（[0021](../frontend/0021-date-library.md)） |

利用者のタイムゾーンの持ち方（設定として保存するか、ブラウザから取得するか）は、認証やユーザーの設計と合わせて決める。

### 理由

- Toggl API の時間記録は UTC の日時で返ってくるため、そのまま UTC で保存すれば変換が要らない
- 保存と受け渡しを UTC に揃えると、タイムゾーンの変換が起きる場所が集計と表示に限られ、変換の誤りを探しやすい
- 「1 日の合計」はどのタイムゾーンで日を区切るかで変わるため、区切りに使うタイムゾーンを明示的に扱う必要がある
- ISO 8601 は人が読める標準の形式で、Java（java.time）、TypeSpec / OpenAPI（`utcDateTime`、`plainDate`）、Temporal のいずれも標準で扱える
- 日付だけの値（集計の期間など）を日時と区別して受け渡すことで、タイムゾーンによる日付のずれを防ぐ

## 比較案

| 案 | 名称 | 特徴 | 判定 |
| --- | --- | --- | --- |
| 1 | UTC で保存し、ISO 8601 で受け渡す | 変換は集計と表示の時だけ | 採用 |
| 2 | 利用者のタイムゾーンで保存する | 保存した値をそのまま表示できる | 見送り |
| 3 | UNIX 時刻（数値）で受け渡す | データが小さい | 見送り |

## 案1: UTC で保存し、ISO 8601 で受け渡す

### 概要

DB と API では日時を常に UTC で扱い、利用者のタイムゾーンへの変換は、集計と画面の表示の時だけ行う方法。

### メリット

- 保存される値が 1 つの基準に揃い、比較や並べ替えが正しく行える
- 利用者がタイムゾーンを変えても、保存したデータを直す必要がない
- ISO 8601 は人が読めて、主要な言語やツールが標準で対応している

### デメリット

- 集計と表示のたびに、タイムゾーンの変換が必要になる
- 日の区切りに使うタイムゾーンを、集計の処理に渡す必要がある

## 案2: 利用者のタイムゾーンで保存する

### 概要

日時を、利用者の現地時刻として保存する方法。

### メリット

- 保存した値をそのまま表示や集計に使える

### デメリット

- 利用者がタイムゾーンを変えたり、夏時間の切り替えがあったりすると、値の意味がずれる
- 複数のタイムゾーンのデータを正しく比較できない

## 案3: UNIX 時刻（数値）で受け渡す

### 概要

日時を、1970 年 1 月 1 日からの秒数やミリ秒数の数値で受け渡す方法。

### メリット

- データが小さく、比較が速い

### デメリット

- 人が読めず、ログや API の確認がしにくい
- 秒かミリ秒かの取り違えが起きやすい
- 日付だけの値を表せない
